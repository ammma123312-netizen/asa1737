# ASA: تشغيل نماذج ضخمة (700 مليار معلمة) على عتاد محدود

> هذا المجلد هو جزء **ASA** من المستودع: أبحاث وأدوات لتشغيل نماذج مفتوحة
> المصدر عملاقة على أجهزة صغيرة أو على GitHub Actions، ثم معالجة البطء الناتج.

---

## 1. الجواب المختصر: هل يشغّل Colibrì نموذجاً بحجم 700 مليار معلمة على GitHub؟

**على المشغّلات المجانية: لا. وعلى مشغّل أكبر أو مشغّل ذاتي (self-hosted): نعم، لكنه بطيء.**

[Colibrì](https://github.com/JustVugg/colibri) محرّك مكتوب بلغة C. يشغّل نموذج GLM-5.2
(744 مليار معلمة، بنية MoE) بذاكرة RAM تقارب 25 جيجابايت. يبقي الأجزاء الكثيفة من
النموذج في الذاكرة، ويقرأ "الخبراء" (experts) من قرص NVMe عند الحاجة. لكن هذه
الطريقة توفّر **الذاكرة فقط، ولا توفّر القرص**: الأوزان نفسها حجمها 429 جيجابايت.

| | مشغّل GitHub المجاني (مستودع عام) | المطلوب لـ GLM-5.2 |
|---|---|---|
| المعالج | 4 أنوية | أي عدد |
| الذاكرة | 16 GB | 16–25 GB كحد أدنى |
| القرص | 14 GB مضمونة (≈70 GB بعد حذف الأدوات المثبتة مسبقاً) | **429 GB** |
| أقصى مدة للمهمة | 6 ساعات | تنزيل 429 GB وحده يستهلك جزءاً كبيراً منها |

لذلك ورشة `asa-colibri` تفحص الجدوى قبل التنزيل، وتوقف المهمة برسالة واضحة إذا كان
النموذج لا يتسع. أما النماذج التي **تعمل فعلاً** على المشغّل المجاني فهي
Qwen3-Coder-30B-A3B (19 GB) وQwen3.6-35B-A3B (23 GB) وOLMoE، وكلها من نوع MoE.

### ✅ تجربة فعلية: بنيت Colibrì وشغّلته بنفسي

جرّبته في حاوية مواصفاتها مطابقة تقريباً لمشغّل GitHub المجاني (4 أنوية، 15 GB RAM، 30 GB قرص)،
باستخدام Colibrì v2.1.0 (commit `0a5504a`) ونموذج Qwen3-Coder-30B-A3B:

| الخطوة | النتيجة |
|---|---|
| `./setup.sh` | 49 ثانية |
| `make qwen36` | 39 ثانية |
| تنزيل الأوزان (19.4 GB) | 73 ثانية |
| `coli doctor` | جاهز (مع تحذير: بعض الخبراء يُقرؤون من القرص، والإقامة المتوقعة في الذاكرة 23%) |
| `coli run --ngen 64` | جواب صحيح في 54 ثانية، تشمل تحميل النموذج |
| `coli serve` + `/v1/chat/completions` | يعمل؛ واجهة متوافقة مع OpenAI |
| سؤال بالعربية (30 رمزاً) | «العاصمة… هي الرياض» في 24 ثانية |
| السرعة الثابتة | **≈2.0 رمز/ثانية** (بين 1.97 و2.16) |
| ذاكرة المحرك | 3.4 GB فقط |

تقدير `asa.planner` لهذا الجهاز كان 1.18 رمز/ثانية، أي ضمن ضعفين من القياس. الاختبار
`test_estimate_matches_measured_run_in_4cpu_container` يثبّت هذه النتيجة.

**وحتى لو نجح التشغيل، يبقى بطيئاً.** هذا ما توقّعته في سؤالك، والأرقام تؤكده:

| الجهاز | سرعة GLM-5.2 المقيسة (حسب Colibrì) | تقدير `asa.planner` |
|---|---|---|
| حاسوب بذاكرة 64 GB وقرص NVMe | ≈0.8 رمز/ثانية | ≈0.5 رمز/ثانية |
| محطة عمل بذاكرة 128 GB | ≈1.83 رمز/ثانية | ≈1.0 رمز/ثانية |
| حاسوب بذاكرة 32 GB وقرص USB خارجي | ≈0.1 رمز/ثانية | — |

بهذه السرعة يستغرق جواب من 200 رمز ما بين **3 و10 دقائق**. لا يمكن تسريع النموذج
الضخم نفسه كثيراً على هذا العتاد، فالحل هو **ألّا يُستخدم النموذج الضخم إلا عند
الحاجة**، وأن يعمل في الخلفية. هذا موضوع القسم 3.

## 2. لماذا هو بطيء؟ (الحساب الذي يعتمد عليه المخطط)

كل رمز (token) يولّده النموذج يتطلب قراءة الأوزان النشطة كلها مرة واحدة:

- في النموذج **الكثيف** (dense)، تُقرأ كل الأوزان مع كل رمز. Llama 405B بتكميم 4 بت
  يعني نحو 243 GB لكل رمز.
- في نموذج **MoE**، تُقرأ أوزان الخبراء المختارين فقط. GLM-5.2 ينشّط نحو 40 مليار
  معلمة، أي ما يقارب 23 GB لكل رمز.

ما يوجد من هذه الأوزان في الذاكرة يُقرأ بسرعة 50–200 GB/ث، وما لا يتسع يُقرأ من القرص
بسرعة 0.3–6 GB/ث. لذلك السرعة ≈ (عرض النطاق) ÷ (البايتات المقروءة لكل رمز). على هذه
المعادلة يُبنى الملف `asa/planner.py`، وقد ضُبط على أرقام Colibrì المنشورة، فيأتي
تقديره ضمن ضعفين من القياس الفعلي.

```bash
python -m asa.planner --list                                    # العتاد والنماذج المعرّفة
python -m asa.planner --hardware gha-free-public --all-models   # ماذا يتسع على المشغّل المجاني؟
python -m asa.planner --hardware gha-free-public --disk-gb 70 --model qwen3-coder-30b-a3b
python -m asa.planner --hardware workstation-128gb --model glm-5.2 --json
```

## 3. البنية المقترحة لحل البطء

```
                    ┌──────────────── LiteLLM (:4000) ─────────────────┐
  واجهة التطبيق ──► │ ذاكرة مؤقتة ──► موجّه (RouteLLM) ──► بدائل احتياطية │
                    └──────┬──────────────────┬───────────────────┬────┘
                           ▼                  ▼                   ▼
                  asa-fast (ثوانٍ)    asa-cloud (ثوانٍ)    asa-big (دقائق)
                  Qwen2.5-3B محلي      Groq / Cerebras       Colibrì + GLM-5.2
                  llama.cpp :8001      مجاني بحدود          :8000 أو GitHub Actions
```

1. **طبقة سريعة**: نموذج صغير محلي (موجود أصلاً في المستودع) يعطي جواباً أولياً فوراً.
2. **طبقة سحابية مجانية**: نموذج 70B على Groq أو Cerebras للأسئلة الأصعب، وسرعته مئات الرموز في الثانية.
3. **طبقة النموذج الضخم**: Colibrì، للمهام التي تحتاج أعلى جودة (البحث المعمّق، المراجعات).
   تعمل **في الخلفية**:
   - محلياً عبر `coli serve` ثم `asa-big` في LiteLLM، بمهلة 30 دقيقة.
   - أو على GitHub: افتح Issue، واكتب السؤال في نصّها، وأضف الوسم `asa-ask`. تعمل
     الورشة وتنشر الجواب تعليقاً عند الانتهاء. البطء هنا لا يزعج أحداً، لأن لا أحد
     ينتظر أمام الشاشة.
4. **ذاكرة مؤقتة**: السؤال المكرر يُجاب من الذاكرة المؤقتة فوراً. استبدلها بـ GPTCache أو
   redis-semantic ليُجاب السؤال *المشابه* أيضاً.
5. **فك الترميز التخميني (Speculative decoding)**: يتوقع النموذج الصغير عدة رموز ويتحقق
   منها الكبير دفعة واحدة. GLM-5.2 في Colibrì يفعل ذلك داخلياً عبر رأس MTP (2–3 رموز لكل تمريرة).
6. **التوزيع**: وضع cluster في Colibrì، أو exo، أو distributed-llama، لتقسيم الخبراء
   على عدة أجهزة يقرأ كل منها من قرصه بالتوازي.

ملف الإعداد: `asa/router/litellm.yaml`. بعد تشغيله يكفي ضبط `LLM_HOSTS=localhost:4000`.

## 6. طريقة التشغيل

**على GitHub**: من تبويب *Actions* اختر **ASA Colibri run** ثم *Run workflow*. النموذج
الافتراضي `qwen3-coder-30b-a3b`. لتشغيل `glm-5.2` اكتب في خانة `runner` اسم مشغّل أكبر
أو `self-hosted`، واختر قيمة `hardware` المناسبة له.

**محلياً**:

```bash
git clone https://github.com/JustVugg/colibri && cd colibri/c
./setup.sh && make qwen36
./coli serve --model /nvme/qwen3-coder-30b --model-id colibri   # http://127.0.0.1:8000/v1
pip install 'litellm[proxy]'
litellm --config asa/router/litellm.yaml --port 4000
# في التطبيق: LLM_HOSTS=localhost:4000
```

## 7. حدود يجب معرفتها

- أرقام المخطط **تقديرات** تقارب الواقع ضمن ضعفين تقريباً، وليست قياسات.
- ذاكرة `actions/cache` في GitHub محدودة بـ 10 GB للمستودع، فتُنزَّل الأوزان من جديد في كل تشغيل.
- AirLLM لم يُجرَّب فعلياً بعد. وهو مصمم أساساً لبطاقات GPU. دعمه لـ CPU موجود منذ الإصدار v2.10.1، لكنه بطيء جداً.
- الوسم `asa-ask` لا يضيفه إلا من لديه صلاحية triage أو أعلى، فلا يستطيع غريب تشغيل الورشة على حسابك.

## 8. مراجعة خطة المستشار التقني

**العتاد المفترض:** بطاقة رسوميات بذاكرة 8 GB، وذاكرة RAM بحجم 16 GB، وقرص NVMe PCIe 4.0 بسرعة 5–7 GB/ث.
أضفته إلى المخطط باسم `consultant-8gbvram`. الأرقام التالية من المخطط، فهي تقديرات وليست قياسات.

```bash
python -m asa.planner --hardware consultant-8gbvram --all-models
python -m asa.planner --hardware consultant-8gbvram --all-models --spec-rows 4 --spec-accept 2.5
```

| السيناريو | بدون تخمين | مع تخمين (4 مسودات، 2.5 رمز لكل تمريرة) |
|---|---|---|
| نموذج كثيف 700B بدقة FP16 (1.4 TB) | 0.004 رمز/ث | 0.011 |
| نموذج كثيف 700B بدقة FP8 (700 GB) | 0.009 | 0.022 |
| نموذج كثيف 700B بتكميم IQ2 (≈180 GB) عبر mmap | 0.037 (≈ 90 دقيقة لكل 200 رمز) | 0.093 |
| **DeepSeek-R1 671B (MoE) بدقة 1.58 بت (131 GB)** | **≈2 رمز/ث** | ≈2 (لا تحسّن) |
| GLM-5.2 744B (MoE) عبر Colibrì | ≈0.43 | ≈0.43 (لا تحسّن) |

### ما هو صحيح في الخطة
- **التشخيص سليم:** عنق الزجاجة هو عرض نطاق PCIe والقرص، وليس قدرة الحساب.
- **أهم بند فيها هو البند الخامس:** الانتقال إلى معمارية MoE. هذا القرار وحده يرفع السرعة
  **أكثر من 50 ضعفاً** مقارنة بأفضل نسخة كثيفة، ولا تقترب منه أي تقنية أخرى في القائمة.
- **التكميم مع mmap** صحيح، وهو ما تفعله llama.cpp مع نسخ Unsloth الديناميكية.

### ما يحتاج تصحيحاً
1. **Colibrì لا يعتمد على "تفريغ طبقي متسلسل"، وسرعته ليست 0.01 رمز/ث.** هو يقرأ من القرص الخبراء
   المختارين فقط في نموذج MoE. سرعته المقيسة مع GLM-5.2 بين 0.8 و1.8 رمز/ث، وجرّبته بنفسي على
   نموذج 30B فأعطى ≈2 رمز/ث (القسم 1). أما AirLLM فهو الذي يحمّل الطبقات بالتسلسل، وسرعة 0.01 تخصّه هو.
2. **فك الترميز التخميني (EAGLE/Medusa) يفيد النماذج الكثيفة فقط، ولا يفيد MoE المقروء من القرص:**
   - في النموذج الكثيف، تُقرأ الأوزان مرة واحدة لكل تمريرة مهما كان عدد الرموز التي يتحقق منها،
     فيرتفع الأداء بقدر عدد الرموز المقبولة. لكنه لا يصل إلى "تقليل القراءة 80%" إلا إذا قُبل 5 رموز
     في كل تمريرة، وهذا نادر في الواقع.
   - في نموذج MoE، كل رمز إضافي يُتحقق منه يستدعي خبراءه الخاصين، فتُقرأ أوزان أكثر. قاس Colibrì
     ذلك: التحقق من رمزين يكلّف ≈1.5 خطوة، ومن ثلاثة ≈2 خطوة. النتيجة أن الربح يكاد يختفي، وهذا
     ما يحسبه الآن `spec_pass_cost` في المخطط. لهذا يستخدم Colibrì رأس MTP مدمجاً بعمق 1 فقط.
3. **DeepSpeed ZeRO-Inference** يتطلب بطاقة NVIDIA ومكتبة libaio، وهو مصمم للإنتاجية بدفعات كبيرة،
   لا لمستخدم واحد ينتظر الجواب. لا يدعم فك الترميز التخميني مباشرة، ولا يغيّر الحساب أعلاه:
   حتى لو تداخل النقل مع الحساب تداخلاً كاملاً، يبقى وقت قراءة 180 GB لكل تمريرة ≈30 ثانية.
4. **PowerInfer** يعمل فقط مع نماذج ذات تنشيط متناثر (ReLU)، مثل ReluLLaMA وProSparse وBamboo.
   لا يوجد نموذج بحجم 700B من هذا النوع، فلا ينطبق على الخطة.
5. **"الخط المتكامل" المقترح** (NVMe ← محرك VRAM بمخزن مزدوج ← نموذج مسودة يتحقق من 6–8 رموز)
   يعطي على نموذج كثيف بحجم 700B نحو **0.15 رمز/ث في أحسن الأحوال**، أي ما يقارب 20 دقيقة لجواب
   متوسط. أما DeepSeek بدقة 1.58 بت عبر llama.cpp، فيعطي على العتاد نفسه وبدون أي تعقيد نحو
   **2 رمز/ث**، وهذا تقدير يحتاج قياساً فعلياً.

### ✅ قياس فعلي: llama.cpp + mmap + نموذج مسودة (مقارنة مباشرة بـ Colibrì)

بنيت llama.cpp (commit `18ab62a`، البناء استغرق 4 دقائق و40 ثانية)، وشغّلته على **الجهاز نفسه وبالنموذج نفسه**
الذي جرّبت عليه Colibrì: Qwen3-Coder-30B-A3B بتكميم Q4_K_M، وحجمه 18.6 GB، وهو **أكبر من ذاكرة
الجهاز (15 GB)**. أي أن جزءاً منه يُقرأ من القرص كما تقترح الخطة. استخدمت الأسئلة الأربعة نفسها
(`python -m asa.bench_api`)، بالترميز الجشع (greedy)، فخرجت النصوص متطابقة في كل الحالات.

| الإعداد | السرعة من الطلب إلى الجواب (بعد التحمية) | سرعة التوليد فقط |
|---|---|---|
| Colibrì int4 (للمقارنة) | 1.97–2.16 رمز/ث | — |
| llama.cpp بالإعدادات الافتراضية | **توقّف: قتله النظام لنفاد الذاكرة** | — |
| llama.cpp + `--no-repack` + mmap | **4.28–4.46 رمز/ث** | 4.7–6.0 (المتوسط 5.15) |
| + نموذج مسودة Qwen3-0.6B، حتى 8 مسودات | 4.76–5.37 | 5.2–6.6 (المتوسط 5.71، **+11%**) |
| + نموذج مسودة، حتى 3 مسودات | 3.60–5.08 | 4.0–6.4 (المتوسط 5.0، **−3%**) |

**ما تعلّمناه من القياس:**
1. **llama.cpp أسرع من Colibrì بأكثر من الضعف** حين لا يزيد النموذج عن الذاكرة إلا قليلاً.
   ميزة Colibrì تظهر حين يكون النموذج **أكبر من الذاكرة بأضعاف** (429 GB مقابل 16 GB)، وهذه الحالة لم نقسها بعد.
2. **فخّ مهم:** llama.cpp يعيد ترتيب الأوزان في الذاكرة افتراضياً (repack)، فيستهلك 13.9 GB من RAM
   ويلغي فائدة mmap، فقتله النظام لنفاد الذاكرة. **مع أي نموذج أكبر من الذاكرة استخدم `--no-repack`.**
   هذا الشرط غائب عن خطة المستشار، ومن دونه لا تعمل الخطة أصلاً.
3. **فك الترميز التخميني على MoE أعطى +11% فقط**، وصار أبطأ بـ 3% حين قلّ عدد المسودات. الخطة
   كانت تَعِد بتقليل القراءة 80%، والقياس يؤكد ما توقعه المخطط: التحقق من رموز إضافية في MoE يستدعي
   خبراء إضافيين.
4. قرص الحاوية يقرأ بسرعة 1.4–1.8 GB/ث. صحّحت هذا الرقم في المخطط، فصار تقديره 3.7 رمز/ث، وهو بين
   قياس المحركين (2.0 و4.4). الاختبار يتحقق من ذلك.

### التوصية
استخدم نموذج **MoE** مكمّماً (DeepSeek-R1/V3 بنسخة Unsloth، أو GLM-5.2 عبر Colibrì)، مع llama.cpp أو
Colibrì، وأبقِ الطبقات الكثيفة وذاكرة KV في الـ 8 GB VRAM. اترك فك الترميز التخميني للنماذج الكثيفة
التي تتسع في الذاكرة، أو لطبقة النموذج الصغير في الموجّه.

### Petals
العميل جاهز في `asa/petals/colab_client.py` للتشغيل على Colab، لكن **لم أجرّبه**. الحاوية التي أعمل
فيها لا تسمح إلا باتصالات HTTPS، وPetals يتصل عبر libp2p. حتى صفحة حالة الشبكة health.petals.dev
لم أستطع الوصول إليها، ولم أجد في البحث تأكيداً بأن الشبكة العامة ما زالت تعمل في 2026. الأمر
`--list` يتحقق من ذلك أولاً. تنبيه مهم: أسئلتك تمرّ عبر خوادم غرباء، فلا ترسل عبرها بيانات خاصة.

## 9. الهدف الأساسي: نموذج 700B بأقل تكلفة

نموذج 30B في الأقسام السابقة كان **اختباراً للأدوات فقط**. الحاوية التي أعمل فيها فيها 30 GB من القرص،
وأصغر نموذج من فئة 700B يحتاج 131 GB. هذا القسم يجيب عن السؤال الأصلي.

**أصغر نسختين متاحتين من فئة 700B:**
- **DeepSeek-R1 671B** بتكميم 1.58 بت عبر llama.cpp: 131 GB.
- **GLM-5.2 744B** بتكميم int4 عبر Colibrì: 429 GB.

| الخيار | التكلفة | DeepSeek 671B | GLM-5.2 744B | الحكم |
|---|---|---|---|---|
| مشغّل GitHub مجاني، أو هذه الحاوية، تقرأ الأوزان من Hugging Face عبر الشبكة | **0** | ≈0.026 رمز/ث (≈2 ساعة لكل جواب) | ≈0.005 (≈12 ساعة) | يعمل نظرياً فقط |
| **خادم مستأجر: 64 GB RAM وقرصا NVMe بسعة 1 TB (مزاد Hetzner)** | **≈35–45 يورو/شهر** | ≈2.6 رمز/ث | ≈0.5–1.1 | **الأفضل قيمة، ويعمل 24/7** |
| مشغّل GitHub كبير (64 نواة، 256 GB) عند الطلب | ≈0.162 $/دقيقة (≈9.7 $/ساعة) | الأوزان تتسع في الذاكرة، والسرعة عالية | ≈0.5 | جيد لجلسة دفعات، لكنه يعيد التنزيل في كل تشغيل |
| حاسوبك + قرص NVMe بسعة 2 TB | ≈150–200 $ مرة واحدة | حسب ذاكرة جهازك | ≈0.5–0.8 مع 64 GB | الأرخص على المدى الطويل إن كان جهازك مناسباً |

**قياس الشبكة:** كل قراءة من Hugging Face تستغرق ≈0.5 ثانية، والسرعة ≈0.08 GB/ث مع 16 قراءة متوازية.
الحساب يؤكد أن تشغيل 700B مجاناً ممكن **تقنياً**، لكن الجواب الواحد يأخذ ساعات. ويتطلب ذلك أيضاً تنزيل
مئات الجيجابايت من Hugging Face في كل تشغيل.

**التوصية:** خادم مستأجر بقرصين NVMe. عليه:
1. Colibrì لنموذج GLM-5.2، أو llama.cpp مع `--no-repack` لنموذج DeepSeek.
2. خادم واجهة OpenAI يتصل به التطبيق عبر LiteLLM.
3. مشغّل GitHub ذاتي على الخادم نفسه، فتعمل ورشة `asa-colibri` والوسم `asa-ask` عليه دون أي تكلفة إضافية.

```bash
python -m asa.planner --hardware hetzner-auction-64gb --all-models
python -m asa.planner --hardware hf-network-stream --model deepseek-r1-1.58bit
```
